# Sprint 3: общий HTTP-контракт

Этот документ дополняет [контракты ЛР2](sprint-2-contracts.md). Пока handlers,
Profile API и runtime отмечены TODO, исполняемого HTTP-сервиса нет. Отдельное
приложенное ТЗ ЛР3 в репозитории отсутствует; численные бюджеты ниже являются
командным предложением и требуют согласования до реализации.

## Идентичность, маршруты и DTO

Один LinkUp HTTP-сервис использует `http.ServeMux` и ровно три бизнес-маршрута:

| Метод и путь | Успех | Ответственный |
| --- | --- | --- |
| `GET /v1/me/discovery?interest=go&limit=2&offset=0` | 200 | Ваня |
| `PUT /v1/me/likes/{targetID}` | 200 | Соня |
| `GET /v1/me/pairs/{targetID}` | 200 | Соня |

`X-Demo-User` обязателен для всех трёх маршрутов: ровно одно десятичное
положительное целое без знака, пробелов и ведущих нулей (например, `7`).
Тот же формат у `targetID` в пути. Диапазон — положительный `int` платформы,
переполнение даёт 400. Текущий пользователь берётся **только** из заголовка
middleware; тело и query не могут его переопределить. Отсутствующий,
повторённый или неверный заголовок даёт 400. `PUT` не имеет тела: непустое
тело даёт 400. `targetID == currentUserID` даёт 409.

Успешные JSON-ответы (отдельные DTO, без автоматической сериализации
`domain.Profile` или `interaction.State`):

```json
{"items":[{"user_id":2,"city":"Moscow","interests":["Go"]}],"limit":20,"offset":0}
{"target_id":2,"liked":true,"liked_by":false,"mutual":false}
```

`liked` означает лайк текущего пользователя цели, `liked_by` — обратный лайк.
`mutual` истинен только при обоих направлениях. У `PUT` и `GET /pairs` один
формат ответа. Повторный допустимый `PUT` возвращает 200 и то же состояние,
не создаёт новую запись и не вызывает `Save`. Отсутствие сохранённой пары при
`GET` возвращает 200 с тремя `false` (`Load` с `found=false`), а не 404.
Это не утверждает существование пользователя с таким ID; необходимость
проверять его отдельно перед чтением пары команда должна согласовать.

Ошибки LinkUp всегда имеют `Content-Type: application/json` и форму
`{"code":"...","message":"..."}`. Сообщение не раскрывает внутренние
ошибки и адреса зависимостей. Обёрнутые ошибки распознаются через `errors.Is`,
типизированные причины — через `errors.As`.

| Причина | HTTP | `code` |
| --- | ---: | --- |
| Неверный header, ID, query или тело | 400 | `invalid_request` |
| Кандидат недоступен для реакции (`usecase.ErrReactionUnavailable`) | 403 | `reaction_unavailable` |
| Нет обязательного пользователя или профиля (`domain.ErrUserNotFound`, `memory.ErrUserNotFound`, `domain.ErrProfileNotFound` в локальном источнике) | 404 | `not_found` |
| Лайк самому себе (`interaction.ErrSameUser`) или запрещённый переход | 409 | `invalid_transition` |
| Обязательный Profile API ответил 5xx, некорректным JSON, слишком большим телом или недоступен | 502 | `dependency_failure` |
| Profile API превысил бюджет | 504 | `dependency_timeout` |
| Другая ошибка чтения/записи или инварианта | 500 | `internal_error` |

Для внешнего Profile API 404 — отсутствие обязательного профиля (404 LinkUp);
его 5xx не маскируется под отсутствие профиля. Неисполненные TODO в каркасе
возвращают отдельный 501 `not_implemented`, который нельзя считать успешным
поведением спринта.
Клиент оборачивает отсутствие через `domain.ErrProfileNotFound`, прочий сбой
через `profileclient.ErrDependency`, timeout через `profileclient.ErrTimeout`.
Первопричина сохраняется через `%w` либо `Unwrap`, чтобы handlers могли
проверять sentinel через `errors.Is` и конкретную сетевую/JSON-ошибку через
`errors.As`.

## Discovery

Источник — `usecase.PairDiscoveryService.Discover` поверх
`matching.NewDiscoveryService` и общего `interaction.Reader`. Порядок
`matching.MatchCandidates` (по убыванию количества общих интересов,
стабильный при равенстве) сохраняется. Входной `ListProfiles` обязан давать
детерминированный порядок; для production источника это нужно проверить.
Сначала выполняются правила поиска и исключения ЛР2, затем фильтр `interest`,
затем пагинация. Фильтр одного непустого интереса сравнивается без учёта
регистра и крайних пробелов, совпадение полное. Если `interest` отсутствует,
дополнительного фильтра нет. `limit` по умолчанию 20, диапазон 1–50.
`offset` по умолчанию 0, неотрицательное целое. Неизвестный параметр,
повторение любого параметра, неверное число и переполнение дают 400.
Пустая выдача сериализуется как `"items":[]`, не `null`.

## Profile API и бюджет

Profile API — отдельный локальный HTTP-процесс. Контракт клиента:
`GET /v1/profiles/{userID}`; `{userID}` имеет тот же формат. `ok` возвращает
200 и JSON `{"user_id":2,"city":"Moscow","interests":["Go"],"available":true}`.
`missing` возвращает 404; `error` — 500; `slow` задерживается дольше бюджета
клиента; `large` возвращает тело больше допустимого. Способ выбора режима
(например, переменная окружения для локального процесса) и тестовые ID
фиксирует Оля до реализации тестов. Чужой/неверный `user_id`, отсутствующие
поля, неверные типы, лишние поля и хвост после JSON считаются ошибкой
зависимости. Ответ 200 должен пройти строгую валидацию до передачи в use case.

Потребитель профиля уже существует: `usecase.EligibilityProfileReader` с
`GetProfile(ctx, userID)`. Для поиска `matching.ProfileRepository` также
требует `ListProfiles(ctx)`. В каркасе HTTP-клиент покрывает `GetProfile`,
а список кандидатов остаётся у локального `memory.Profiles`. Если команда
решит получать и список по HTTP, контракт Profile API следует расширить
согласованно; нельзя подменять `ListProfiles` фиктивным ответом.

Предлагаемый бюджет одной команды реакции — 800 мс от HTTP-входа, включая
Profile API. Один переиспользуемый `http.Client` имеет timeout 500 мс;
каждый запрос использует входной `context.Context`. Максимум тела ответа
Profile API — 64 КиБ (проверка чтением максимум `64 КиБ + 1`). При timeout
обязательной зависимости — 504, остальных сбоях — 502. Конфигурация через
environment: адреса LinkUp и Profile API, base URL клиента, timeout клиента,
лимит тела и серверные таймауты. Предлагаемые серверные значения: чтение
заголовков 2 с, чтение 5 с, запись 5 с, idle 30 с, shutdown 10 с.

## Runtime, конкурентность и завершение

`X-Request-ID` генерируется для каждого запроса и возвращается в ответе;
структурированный `log/slog` записывает ID, метод, путь, статус и длительность.
Middleware учебной идентичности кладёт проверенный ID в context. Сервис
использует один экземпляр pair-store для `React`, `Discover` и `GET /pairs`.

`interaction.Reader.Load` и `Store.Save` должны быть безопасны при параллельных
вызовах. Одних mutex внутри этих двух методов недостаточно: последовательность
`React` (`Load` → `ApplyLike` → `Save`) должна быть атомарна для пары, иначе
одновременные встречные лайки теряются. Арина согласует с владельцами use case
минимальный способ сериализации команды по паре без изменения публичных
интерфейсов ЛР2. Тесты с `-race` должны проверить встречные и повторные лайки.
При SIGINT/SIGTERM сервер прекращает приём, ждёт активные запросы не дольше
shutdown budget, затем закрывает ресурсы. Технические ошибки нельзя считать
успешным лайком или состоянием пары.

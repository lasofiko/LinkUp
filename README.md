# LinkUp

LinkUp — учебный проект на Go для подбора пользователей по городу и общим
интересам, обработки направленных лайков и определения взаимности.

В проекте есть консольные демонстрации, HTTP-сервис LinkUp и отдельный
локальный mock-сервис Profile API. Данные хранятся в памяти. PostgreSQL,
миграции, веб-интерфейс и чат в этой версии не реализованы.

## Реализованные возможности

### Подбор пользователей

`matching.MatchCandidates`:

- исключает самого пользователя и недоступные профили;
- отбирает кандидатов из того же города хотя бы с одним общим интересом;
- сравнивает город и интересы без учёта регистра и пробелов по краям;
- считает каждый общий интерес один раз;
- сортирует по убыванию количества общих интересов;
- сохраняет исходный порядок при равном количестве совпадений;
- не изменяет входные данные и копирует срезы интересов в результате.

`matching.DiscoveryService` получает профиль пользователя и список профилей
из репозитория, затем вызывает `MatchCandidates`.

`usecase.PairDiscoveryService` дополнительно читает общее состояние пар.
Из выдачи исключаются кандидаты, которым текущий пользователь уже поставил
лайк, и взаимные пары. Входящий лайк сам по себе не скрывает отправителя
от получателя. Порядок оставшихся кандидатов сохраняется.

### Лайки и состояние пары

`interaction.Pair` — канонический ключ пары: меньший ID хранится первым.
`interaction.State` хранит два направления лайка. Взаимность возникает,
когда записаны оба направления.

`usecase.ReactService.React(ctx, fromUserID, toUserID)`:

1. Проверяет context, получает обоих пользователей и профиль получателя.
2. Создаёт каноническую пару и читает её состояние.
3. Проверяет допустимость реакции и применяет `interaction.ApplyLike`.
4. Сохраняет изменённое состояние и возвращает результат.

Отсутствующая пара считается начальным состоянием. Повтор уже принятого
лайка при сохранении допустимости действия успешен и не записывает состояние
повторно. При ошибке команда возвращает нулевой результат и ошибку;
ошибки зависимостей оборачиваются с сохранением причины для `errors.Is`.

В HTTP-сервисе используется один экземпляр `memory.PairStore` для реакций,
discovery и чтения пары. Он сериализует изменение состояния одной пары,
чтобы конкурентные встречные лайки не перезаписывали друг друга.

`interaction.Memory` используется в последовательном консольном демо
и тестах второго спринта. Его `Load` и `Save` защищены mutex, но вся
последовательность чтения, изменения и записи не является атомарной.
Для конкурентных реакций HTTP-сервис использует `memory.PairStore`.

Старые `RestrictedDiscoveryService`, `Likes`, `Matches` и `MatchService`
сохранены для прежних демонстраций и тестов. Они не являются вторым
хранилищем состояния пар в HTTP-сервисе.

### HTTP-сервис

`cmd/linkup` собирает обработчики, middleware и зависимости. Реализованы
учебная идентичность через `X-Demo-User`, генерация `X-Request-ID`,
структурированные логи через `log/slog`, таймауты сервера и завершение
с ожиданием активных запросов в пределах shutdown budget.

Лайки и чтение пары доступны по HTTP. Для HTTP-discovery остаётся ошибка
передачи идентичности; её описание приведено в разделе
[«Известные ограничения»](#известные-ограничения).

## Структура проекта

```text
cmd/
  discovery/       Консольный сценарий discovery, лайков и взаимности
  server/          Прежнее консольное демо пользователей и ограничений
  linkup/          HTTP-сервис LinkUp
  profile-api/     Отдельный mock-сервис Profile API

internal/
  domain/          Общие модели и доменные ошибки
  interaction/     Пара, состояние, чистый переход лайка и Memory
  matching/        Поиск, ранжирование и прежняя логика результата Match
  usecase/         Прикладные сценарии и интерфейсы зависимостей
  handler/         HTTP-обработчики и middleware
  profileclient/   HTTP-клиент Profile API
  profilemock/     Mock Profile API и переключение его режимов
  repository/
    memory/        Хранилища в памяти, включая PairStore
    postgres/      Заготовки PostgreSQL-реализаций
  config/          Конфигурация HTTP-runtime из environment

docs/              Контракты и планирование спринтов
migrations/        Пустые заготовки SQL-миграций
web/               Заготовки веб-интерфейса
```

## Требования

- Go `1.27.1`, согласно `go.mod`.
- Git для работы с репозиторием.
- `golangci-lint` для запуска линтера.

PostgreSQL и Docker для описанных ниже демонстраций не требуются.
`Dockerfile`, `docker-compose.yml` и `Makefile` пока являются пустыми
заготовками. Конфигурация читается из переменных окружения;
автоматической загрузки файла `.env` нет.

Все команды ниже выполняются из корня репозитория.

## Консольные демонстрации

### Полный сценарий второго спринта

```sh
go run ./cmd/discovery
```

Демо создаёт собственных пользователей и профили в памяти, показывает
выдачу до лайков, первый лайк, ответный лайк, взаимность и повтор команды.
HTTP-сервисы для этого запуска не нужны.

Ожидаемые ID кандидатов в порядке выдачи:

| Этап | Пользователь 1 | Пользователь 2 |
| --- | --- | --- |
| До лайков | `[2, 3]` | `[1, 6]` |
| После лайка 1 → 2 | `[3]` | `[1, 6]` |
| После ответного лайка 2 → 1 | `[3]` | `[6]` |

После ответного лайка `IsMutual=true`. Повтор 1 → 2 возвращает `err=<nil>`
и прежнее состояние пары.

### Прежнее консольное демо

```sh
go run ./cmd/server
```

Несмотря на имя каталога, эта команда запускает консольную программу.
Она показывает пользователя, допустимость реакции 1 → 2 (`allowed`)
и поиск с ограничениями через прежние `Likes` и `Matches`.

Ожидаемая часть вывода:

```text
Eligibility 1 -> 2: allowed
Expected candidate IDs: [2]
Actual candidate IDs: [2]
```

## Запуск HTTP-сервисов

В первом терминале запустите Profile API:

```sh
go run ./cmd/profile-api
```

По умолчанию он слушает `127.0.0.1:8081` и начинает работу в режиме `ok`.

Во втором терминале запустите LinkUp:

```sh
go run ./cmd/linkup
```

По умолчанию LinkUp слушает `:8080`; локальный адрес для запросов —
`http://127.0.0.1:8080`. Сервис использует демонстрационных пользователей
с ID 1–5. Пользователь 3 недоступен для реакции.

Для лайка LinkUp читает профиль получателя через Profile API.
Список профилей и профиль текущего пользователя для discovery остаются
локальными. Данные консольных программ и HTTP-процессов независимы.

### Маршруты LinkUp

| Метод | Путь | Назначение |
| --- | --- | --- |
| `PUT` | `/v1/me/likes/{targetID}` | Поставить лайк и вернуть состояние пары |
| `GET` | `/v1/me/pairs/{targetID}` | Прочитать состояние пары |
| `GET` | `/v1/me/discovery` | Discovery с фильтром и пагинацией; сейчас есть известная ошибка идентичности |

`X-Demo-User` обязателен. Заголовок и `targetID` должны содержать одно
положительное десятичное целое без знака, пробелов и ведущих нулей,
в диапазоне `int` платформы. Повтор заголовка запрещён.
ID текущего пользователя для лайков и чтения пары берётся из context,
который заполняет middleware на основе заголовка.

У `PUT /likes` тело должно быть пустым. Query-параметры у `/likes` и `/pairs`
не допускаются. Действие с самим собой возвращает `409`.

Оба маршрута пары возвращают JSON следующего вида:

```json
{"target_id":2,"liked":true,"liked_by":false,"mutual":false}
```

`liked` — исходящий лайк, `liked_by` — входящий, `mutual` — взаимность.
Если сохранённой пары нет, `GET /pairs` возвращает `200` и три `false`.
Этот маршрут отдельно не проверяет существование участников пары.

### Пример лайков в PowerShell

Пример рассчитан на только что запущенные сервисы и Profile API в режиме `ok`.
Выполните команды в третьем терминале:

```powershell
$base = 'http://127.0.0.1:8080'

# Пользователь 1 ставит лайк пользователю 2.
Invoke-RestMethod -Method Put -Uri "$base/v1/me/likes/2" -Headers @{ 'X-Demo-User' = '1' }

# Пользователь 2 отвечает лайком пользователю 1.
Invoke-RestMethod -Method Put -Uri "$base/v1/me/likes/1" -Headers @{ 'X-Demo-User' = '2' }

# Пользователь 1 читает состояние пары.
Invoke-RestMethod -Method Get -Uri "$base/v1/me/pairs/2" -Headers @{ 'X-Demo-User' = '1' }
```

После первой команды: `liked=true`, `liked_by=false`, `mutual=false`.
После ответного лайка оба направления и `mutual` равны `true`.
Последний запрос возвращает `target_id=2` и три `true`.
PowerShell отображает JSON-ответ как объект.

### Ошибки лайка и чтения пары

| HTTP | `code` | Причина |
| --- | --- | --- |
| 400 | `invalid_request` | Неверные ID, заголовок, query или непустое тело лайка |
| 403 | `reaction_unavailable` | Профиль получателя недоступен для реакции |
| 404 | `not_found` | Нет обязательного пользователя или профиля при реакции |
| 409 | `invalid_transition` | Попытка взаимодействия с самим собой |
| 502 | `dependency_failure` | Ошибка обязательного Profile API |
| 504 | `dependency_timeout` | Превышен таймаут Profile API |
| 500 | `internal_error` | Прочая внутренняя ошибка |

Ошибки этих бизнес-обработчиков имеют JSON-форму:

```json
{"code":"invalid_request","message":"invalid request"}
```

## Режимы Profile API

Mock предоставляет `GET /v1/profiles/{userID}`. В режиме `ok` существуют
профили 1–5. Другой корректный ID возвращает `404`.

Для профиля 2 успешный ответ:

```json
{"user_id":2,"city":"Moscow","interests":["Go"],"available":true}
```

Режим переключается через `PUT /__admin/mode/{mode}` без `X-Demo-User`:

```powershell
Invoke-RestMethod -Method Put -Uri 'http://127.0.0.1:8081/__admin/mode/slow'

# Вернуть обычную работу после проверки.
Invoke-RestMethod -Method Put -Uri 'http://127.0.0.1:8081/__admin/mode/ok'
```

| Режим | Поведение Profile API | Результат допустимого лайка в LinkUp при стандартных настройках |
| --- | --- | --- |
| `ok` | Возвращает профиль | 200 для доступного получателя |
| `missing` | Возвращает 404 | 404 `not_found` |
| `error` | Возвращает 500 | 502 `dependency_failure` |
| `slow` | Задерживает ответ на 2 секунды | 504 `dependency_timeout` |
| `large` | Возвращает профиль с телом больше 64 КиБ | 502 `dependency_failure` |

Режим действует на весь экземпляр mock-сервиса. Для проверки ошибок лайка
используйте существующих разных пользователей, например 1 → 2.

Клиент Profile API переиспользует `http.Client`, передаёт context запроса,
ограничивает размер ответа и проверяет структуру JSON, обязательные поля,
ID профиля, неизвестные поля и отсутствие лишнего JSON после ответа.

## Конфигурация

Переменные окружения процесса LinkUp:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `LINKUP_ADDR` | `:8080` | Адрес LinkUp |
| `PROFILE_API_ADDR` | `127.0.0.1:8081` | Основа стандартного URL клиента Profile API |
| `PROFILE_BASE_URL` | `http://` + `PROFILE_API_ADDR` | Явный base URL клиента Profile API |
| `PROFILE_TIMEOUT` | `500ms` | Таймаут HTTP-клиента Profile API |
| `PROFILE_MAX_BODY` | `65536` | Максимальный размер ответа Profile API в байтах |
| `LINKUP_COMMAND_TIMEOUT` | `800ms` | Бюджет context входящего запроса |
| `LINKUP_READ_HEADER_TIMEOUT` | `2s` | Таймаут чтения заголовков |
| `LINKUP_READ_TIMEOUT` | `5s` | Таймаут чтения запроса |
| `LINKUP_WRITE_TIMEOUT` | `5s` | Таймаут записи ответа |
| `LINKUP_IDLE_TIMEOUT` | `30s` | Таймаут неактивного соединения |
| `LINKUP_SHUTDOWN_TIMEOUT` | `10s` | Бюджет завершения сервера |

Адрес отдельного процесса `cmd/profile-api` также задаётся через
`PROFILE_API_ADDR`. Environment задаётся отдельно в каждом терминале.

Пример для PowerShell с изменёнными портами:

```powershell
# Терминал Profile API.
$env:PROFILE_API_ADDR = '127.0.0.1:8082'
go run ./cmd/profile-api
```

```powershell
# Терминал LinkUp.
$env:LINKUP_ADDR = '127.0.0.1:8083'
$env:PROFILE_BASE_URL = 'http://127.0.0.1:8082'
go run ./cmd/linkup
```

`config.Load` также читает `PROFILE_API_READ_HEADER_TIMEOUT`,
`PROFILE_API_READ_TIMEOUT`, `PROFILE_API_WRITE_TIMEOUT`,
`PROFILE_API_IDLE_TIMEOUT` и `PROFILE_API_SHUTDOWN_TIMEOUT`, но отдельный
`cmd/profile-api` пока не применяет эти значения. Его серверные таймауты
фиксированы: 2 с для заголовков, 5 с для чтения и записи, 30 с для idle,
10 с для shutdown.

## Проверки

```sh
gofmt -l .
go build ./...
go test ./... -count=1
go vet ./...
go test -race ./... -count=1
golangci-lint run
```

У `gofmt -l .` не должно быть вывода. Для исправления используйте
`gofmt -w` с путями изменённых файлов.

Целевые проверки:

```sh
# Интеграционный цикл discovery и реакций второго спринта.
go test ./cmd/discovery -run TestIntegration_DiscoveryAndReactLifecycle -count=1 -v

# Переходы состояния и память второго спринта.
go test ./internal/interaction -count=1 -v

# Команда реакции, включая отказ записи и повторную попытку.
go test ./internal/usecase -run '^TestReact' -count=1 -v

# Прежняя логика результата Match.
go test ./internal/matching/test ./internal/usecase/tests -count=1 -v

# Конкурентные реакции через PairStore.
go test -race ./internal/repository/memory -count=1 -v
```

На Windows, если линтер установлен в стандартный каталог Go, но не найден
в `PATH`, его можно вызвать из PowerShell:

```powershell
& (Join-Path $env:USERPROFILE 'go\bin\golangci-lint.exe') run
```

GitHub Actions запускает форматирование, сборку, тесты, `go vet` и линтер.
GitLab CI запускает форматирование, сборку, тесты, `go vet` и `-race`.
Успешность CI проверяется для конкретного коммита или PR.

## Известные ограничения

- Данные находятся в памяти каждого процесса и теряются при его завершении.
- В HTTP-discovery middleware записывает ID через `WithCurrentUserID`,
  а обработчик читает другой ключ `CtxKeyUserID`. Поэтому запрос к
  `/v1/me/discovery` с корректным `X-Demo-User` сейчас возвращает 400
  `invalid_request` с сообщением `no known user id`. Консольный поиск
  и сценарий второго спринта этой ошибкой не затронуты.
- В обработчике discovery остаются ошибки валидации query: пустые
  `limit`/`offset` и некоторые некорректные query могут быть приняты как
  значения по умолчанию. Отсутствующий локальный профиль отображается
  как 500 вместо предусмотренного контрактом 404. Эти ветви обработки
  нужно исправить наряду с передачей ID пользователя.
- Настройки серверных таймаутов Profile API пока не подключены к
  `cmd/profile-api`; фактические значения приведены выше.
- Долговременное хранение, PostgreSQL-репозитории, SQL-миграции,
  редактирование профиля, веб-интерфейс и чат в этой версии не реализованы.

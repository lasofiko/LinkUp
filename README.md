# LinkUp

LinkUp — учебный проект на Go для подбора пользователей по городу
и общим интересам, обработки лайков и определения взаимных совпадений.

В первом спринте реализуется бизнес-логика с хранением данных в памяти.
Демонстрация выполняется через консольные программы.

## Реализованные возможности

### Discovery по городу и интересам

Функция `MatchCandidates`:

- исключает текущего пользователя и недоступные профили;
- отбирает профили из того же города с общими интересами;
- сравнивает город и интересы без учёта регистра и пробелов по краям;
- учитывает каждый общий интерес один раз;
- сортирует кандидатов по убыванию числа общих интересов;
- сохраняет исходный порядок при равном количестве совпадений;
- не изменяет исходные данные и копирует вложенные срезы интересов.

`DiscoveryService` получает профиль пользователя и список профилей,
после чего вызывает фильтрацию.

### Контракт B: Discovery с ограничениями

`RestrictedDiscoveryService` получает профили, исходящие лайки
и существующие Match текущего пользователя.

Из результата исключаются:

- текущий пользователь;
- недоступные профили;
- пользователи, которым уже поставлен лайк;
- пользователи, с которыми уже существует Match.

Порядок оставшихся профилей сохраняется. Если подходящих кандидатов нет,
возвращается пустой срез без ошибки.

Сервис использует общие in-memory-хранилища `Profiles`, `Likes` и `Matches`.
Ошибки источников оборачиваются с сохранением возможности проверки
через `errors.Is`.

Базовый Discovery и Discovery с ограничениями пока представлены
отдельными сервисами.

### Контракт D: результат Match

`MatchService` проверяет лайки в обе стороны и наличие существующего Match.

Возможные результаты:

- `NoMatch` — взаимного лайка нет;
- `MatchCreated` — взаимный лайк есть, новый Match сохранён;
- `ExistingMatch` — Match уже существует.

Пара пользователей хранится в едином порядке, поэтому пары `(A, B)`
и `(B, A)` соответствуют одному Match.

### Общие модели

- `User` — данные аккаунта.
- `Profile` — город, интересы и доступность пользователя.
- `Interest` — интерес пользователя.
- `Reaction` — направленная реакция на другого пользователя.
- `Match` — совпадение между двумя пользователями.
- `Message` — модель сообщения.

Наличие модели не означает, что соответствующий пользовательский
сценарий уже реализован полностью.

## Структура проекта

```text
cmd/
  server/       Демонстрация пользователя и контракта B
  discovery/    Демонстрация подбора по городу и интересам

internal/
  domain/       Общие модели и доменные ошибки
  matching/     Логика подбора и определения результата Match
  usecase/      Сервисы сценариев и интерфейсы зависимостей
  repository/
    memory/     Хранилища в памяти
    postgres/   Заготовки PostgreSQL-реализаций
  handler/      Заготовки обработчиков
  config/       Заготовка конфигурации

docs/           Документация и демо-чек-лист
migrations/     Заготовки миграций
web/            Заготовки веб-интерфейса
```

Сейчас `DiscoveryService` находится в `internal/matching`.
Его перенос в `internal/usecase` остаётся задачей согласования архитектуры.

## Требования

- Go согласно версии в `go.mod`: `1.27.1`.
- Git.
- Для проверки линтером — `golangci-lint`.
  Локальная объединённая версия проверена с `golangci-lint 2.14.0`.

PostgreSQL и Docker для текущих консольных демо не требуются.

## Запуск

Все команды выполняются из корня проекта.

### Демо контракта B

```bash
go run ./cmd/server
```

Несмотря на название каталога, сейчас это консольное демо,
а не HTTP-сервер.

Ожидаемая часть вывода:

```text
Contract B: restricted discovery
Expected candidate IDs: [2]
Actual candidate IDs: [2]
```

### Демо Discovery по городу и интересам

```bash
go run ./cmd/discovery
```

Для подготовленных данных ожидаются пользователи `2` и `3`
в указанном порядке.

### Проверка контракта D

```bash
go test ./internal/matching/test ./internal/usecase/tests -v -count=1
```

Тесты демонстрируют отсутствие Match, взаимный лайк, создание Match
и повторное обращение без дублирования.

## Проверки

```bash
go build ./...
go test ./... -count=1
go vet ./...
golangci-lint run
```

Если на Windows линтер установлен в стандартную папку Go,
но недоступен через `PATH`, в PowerShell можно использовать:

```powershell
$lintExe = Join-Path $env:USERPROFILE "go\bin\golangci-lint.exe"
& $lintExe run
```

Успешная проверка линтером завершается с кодом `0`.

Workflow `.github/workflows/ci.yml` содержит сборку, тесты,
`go vet` и запуск линтера. Успешность CI нужно проверять
для конкретного опубликованного коммита или PR.

## Тестирование

Тестами покрыты:

- фильтрация кандидатов и порядок результатов;
- исключение недоступных, лайкнутых и уже совпавших пользователей;
- корректный пустой результат;
- сохранение исходных данных и вложенных срезов;
- обработка ошибок источников данных;
- распознавание ошибок через `errors.Is`;
- чтение ограничений из общих хранилищ;
- определение и сохранение Match;
- повторное обращение и обратный порядок участников Match.

Тесты расположены рядом с реализациями, а также в
`internal/matching/test` и `internal/usecase/tests`.
Команда `go test ./...` запускает их все.

## Ограничения текущей версии

- Данные хранятся в памяти и теряются после завершения программы.
- HTTP API, PostgreSQL, миграции и веб-интерфейс пока не реализованы.
- Создание Match не оформлено как атомарная операция
  проверки и сохранения для конкурентных запросов.
- Отдельное консольное демо контракта D ещё не добавлено.
- Реализацию контракта C и общий сценарий всех четырёх контрактов
  необходимо подтвердить перед закрытием спринта.
- Модели сообщений и реакций сами по себе не являются готовым чатом
  или полным сценарием обработки реакций.

## Работа с изменениями

Изменения разрабатываются в feature-ветках и проходят проверку перед
объединением в `dev`.
